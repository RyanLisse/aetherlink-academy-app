The Daily Brief Lab: How an AI-Native Workflow Works
01

What this lab builds

One morning brief, seven steps, and a repository that starts out empty on purpose.

Picture Tuesday, 8:00 in the morning

You open one page. It tells you which code reviews are waiting, which tickets moved overnight, which wiki page someone edited, and what is on your calendar. You did not write it. An agent did.

That is the thing this lab builds: a daily brief agent. It reads your work tools every morning and writes a one-page brief.

🦊

Code reviews

GitLab at work, or GitHub on your own.

🎫

Tickets

Jira at work, or Linear on your own.

📚

Team wiki

Confluence at work, or Notion on your own.

📅

Calendar

The Outlook calendar, read through Microsoft's API.

🔒
Read, never write

The agent only reads these sources. It never posts a comment, closes a ticket or sends an email. You will see this rule come back in almost every document of the lab.

The surprise: there is almost no code

Open the repository and you find documents, not software. The branch called main holds templates and a package skeleton. Nothing else.

PLAIN ENGLISH

Four columns: which step, which phase of the work, what you produce, and how anyone can tell it is finished.

(Table divider, required by Markdown.)

Step 1: write down what you want. Done when a human accepts where the fence is.

Step 2: describe the brief's exact shape, then write tests that check it. Done when those tests pass.

Step 3: design the parts, record one decision (an ADR), write a plan. Done when a stranger could follow it.

Step 4: the first real code. Done when a sample brief turns into an HTML page.

Step 5: connect the real sources. Done when tests and the typecheck pass without touching the internet.

Step 6: record proof. Done when three commands, their exit codes and a second person are written down.

Step 7: a human decides whether to ship, quoting the line that convinced them.

💡
Every step has a "how would I know?"

Notice that no row says "done when it feels finished." Each proof is something another person can check without you in the room. That habit is what lets you trust work an AI did for you.

02

Intent: drawing the fence

Before anyone writes a line of code, one page says what the agent is for and where it may never go.

Surveyors come before builders

Before a house goes up, a surveyor hammers stakes into the ground: this is the plot, that is the neighbour's land. Nobody argues about the fence later because it was agreed before the first brick.

intent.md is those stakes. It is step 1 of the lab, and AGENTS.md tells the AI assistant to read it before changing anything.

1
Outcome

One observable result in plain words: what the reader opens each morning, and what they no longer have to do.

2
Success checks

Tick-boxes a stranger can verify with one command or one look.

3
Boundary

What is in scope, what is forbidden, and when to stop and ask a human.

4
Owners

Three named roles: the Reader, the Maintainer and the Gate.

5
Evidence contract + OPEN

What counts as proof, and a list of every unknown, written down instead of guessed.

Success checks: written for a stranger

The template's own placeholder text tells you how to write a good check. Read the hints closely; they are the lesson.

intent.md 
## Success checks

- [ ] `TEMPLATE — a check a fresh reader can verify with one command or one look, without the author in the room.`
- [ ] `TEMPLATE`
- [ ] `TEMPLATE`
- [ ] `OPEN — a check that needs a live run or an access you do not have yet.`
PLAIN ENGLISH

A section heading. The ## is Markdown for "second-level heading."

 

Check one: someone who has never met you must be able to confirm it, by running a command or glancing at a page.

Check two: same rule.

Check three: same rule.

Check four is honest about what you cannot prove yet, like a live run you have no access for. It is marked OPEN, not quietly dropped.

💡
"Without the author in the room"

This phrase is the key to working with AI. The AI is always "the author who is not in the room" tomorrow. If a check needs you to explain it, it cannot catch a mistake the AI made while you were not looking.

The boundary: four stakes in the ground

This is the most important block in the whole lab. Every later document points back to it.

intent.md 
## Boundary

- In scope: `TEMPLATE — the folder, the sources, the outputs.`
- Out of scope: `TEMPLATE — what the agent may never do: write to a source, send anything, store a credential.`
- The model never invents a fact: `TEMPLATE — what happens when a source is silent.`
- Stop or escalate when: `TEMPLATE — a write scope is offered, personal data appears, the agent starts deciding instead of describing.`
PLAIN ENGLISH

The fence itself.

 

Inside the fence: which folder the work lives in, which tools get read, what files come out.

Outside the fence: never change anything in a source, never send a message, never keep a credential.

If a source says nothing (say, the calendar is empty), the brief must say that, not make something up. This guards against hallucination.

Tripwires: if someone offers a write scope, if private data shows up, or if the agent starts making decisions instead of describing facts, halt and hand it to a human.

Wish or rule?

SOLO.md gives you a test for your own boundary: "Read the boundary aloud. If any line is a wish rather than a rule, it is NEEDS REVISION." Try it on this made-up draft. Click the line that is a wish.

Three owners, three different jobs

📖
Reader

"Reads the brief, decides what to push." The person the agent works for.

🔧
Maintainer

"Owns the contract, the prompt, the schedule." Fixes it when it breaks.

🚦
Gate

"Reads every pull request against this file before merge." The human who says yes or no.

Splitting these roles means nobody grades their own homework, including the AI.

03

Flight plan before takeoff

Spec, design and plan: three documents that turn a wish into steps an AI can execute and a stranger can check.

Pilots file a plan before they fly

No pilot takes off and "sees where it goes." They file where they are landing, which aircraft they are flying, and the checkpoints on the way. Air traffic control can then tell, at any moment, whether the flight is on course.

Steps 2 and 3 of the lab are that filing. Three documents, three questions:

📐

docs/spec.md

The destination. Exactly what the brief looks like, field by field, quoted from the example PDFs.

🧩

docs/design.md

The aircraft. Which part owns which job, and what each part must never do.

🗺️

docs/plan.md

The checkpoints. Ordered steps, exact files, one proof command per step.

⚖️

docs/decisions/

The logbook. One ADR per real decision, so nobody re-argues it next month.

The spec: every field needs a quote

The spec's heart is the contract, a table that pins down each piece of data the brief contains. The key column is the last one: every rule must be backed by real words from the reference PDFs.

docs/spec.md 
## The contract

| Field | Type | Rule | Example from the reference |
| --- | --- | --- | --- |
| `TEMPLATE` | `TEMPLATE` | `TEMPLATE — imperative, max nine words, names the artifact` | `TEMPLATE — quoted from the PDF` |
PLAIN ENGLISH

The contract: the agreed shape of a brief.

 

For each field: its name, its type, the rule it obeys, and a real example.

(Table divider.)

One example rule style: "imperative, max nine words, names the artifact." Precise enough that a test can check it. The example must be quoted, not invented.

Step 2 then works test-first: test/schema.test.ts is written and fails, and only then does src/brief.ts get written to make it pass. SOLO.md even asks you to check that "git log show[s] the test commit before brief.ts."

The design: boundaries become code

The design template has a section that is easy to skim past and is the most important one. It asks how each rule from intent.md is enforced by the program itself, not by asking the AI nicely.

docs/design.md 
## Boundaries in code

- Bound the task: `TEMPLATE — which options remove capability from the model.`
- Watch the loop: `TEMPLATE — which options cap and log the run.`
- Interrupt on purpose: `TEMPLATE — where the human sits, and why not inside the run.`

## Hooks (deterministic, hold without asking)

- `TEMPLATE — the rule from the prompt that must hold even if the model ignores the prompt, and the code that holds it.`
PLAIN ENGLISH

How the fence from intent.md is built into the software.

 

Take abilities away: the model simply is not given a shell or a write tool, so it cannot misuse one.

Put a limit on how many steps the agent loop can take, and log every tool call.

The human reviews after the run, not in the middle. A 3 a.m. scheduled job cannot wait for someone to click "allow."

 

Hooks: rules enforced by plain code, every time.

If a rule matters, do not trust the prompt alone. Write code that holds it even if the model ignores the instructions.

💡
A prompt is a request. Code is a lock.

"Please don't write anything" in a prompt usually works. Not handing the model a write tool always works. When a rule really matters, ask your AI assistant to remove the capability, not to add a sentence to the prompt.

The plan: checkpoints you can actually run

The plan's step table has a Proof command column. Those commands are real; they live in package.json, the one piece of real configuration on main.

AGENTS.md: the rules that stop AI from bluffing

Three of the seven rules are aimed squarely at the ways AI assistants go wrong.

AGENTS.md 
2. Verify the current state with the relevant command. Do not invent evidence, exit codes, screenshots or run results. Quote actual output; mark unrun checks `OPEN`.
3. The agent you build is read-only by construction: no built-in tools, only the source tools you define, no write scope on any token. Never widen that.
4. Never put a credential, a token or private company data in this repository, a prompt or a document. Sample data lives in `sample/`.
PLAIN ENGLISH

No bluffing. Run the command; do not guess what it would say. If you did not run it, say OPEN. This targets AI's habit of confidently reporting "all tests pass" without running them.

No extra powers. "Built-in tools" are things like a shell or file editor. The brief agent gets none of them, only the read-only source tools you write.

No secrets. A token pasted into a prompt or committed to the repo can leak. Real tokens live only in a local .env file that Git ignores.

💡
Two kinds of agent, two sets of rules

There are two AIs in this lab: your coding assistant (which writes the code) and the brief agent (which the code becomes). AGENTS.md governs the first and fences in the second. Keeping them apart in your head is half the battle.

Evidence and the gate

How the lab turns "it works" into a claim someone else can check, and who gets to say yes.

Inside the courtroom

A court does not accept "trust me." It wants exhibits, a witness who can be cross-examined, and a judge who reads them and rules. When the evidence is not in yet, the case is adjourned, which is not the same as losing.

Steps 6 and 7 run the same way. docs/evidence.md holds the exhibits. docs/gate.md records the ruling.

✅

PASS

Proven. A command ran, the output is quoted, and a second person reran it.

❌

FAIL

It ran and the result contradicts the claim.

⏸️

OPEN

Not yet known. Unrun, or blocked by access. "A blocked credential is an access result, not a failure."

The evidence table

Look at how much the template demands per row. Each column closes a gap an overconfident author (human or AI) could slip through.

docs/evidence.md 
Every row is a claim with the command that proves it, the exit code you saw and
the person who reran it. A row without a reviewer is a hypothesis. A command
nobody ran is `OPEN`, never a failure and never a pass.

| Claim | Command | Exit code | Output line quoted | Reviewer | Status |
| --- | --- | --- | --- | --- | --- |
| `TEMPLATE — the types hold` | `npm run typecheck` | `OPEN` | `OPEN` | `TEMPLATE` | `OPEN` |
| `TEMPLATE — the contract holds` | `npm test` | `OPEN` | `OPEN` | `TEMPLATE` | `OPEN` |
| `TEMPLATE — the page renders` | `npm run brief:sample` | `OPEN` | `OPEN` | `TEMPLATE` | `OPEN` |
PLAIN ENGLISH

Each row pairs a claim with the command that proves it...

...and a second person. Without that second person it is only a hypothesis.

Not run = OPEN. Never quietly counted as a pass, never unfairly counted as a fail.

 

Six columns: what you claim, how to check it, the exit code, a copied line of real output, who reran it, and the verdict.

(Table divider.)

Claim 1: all data shapes line up. Proof: the typecheck.

Claim 2: the brief's contract from the spec holds. Proof: the test suite.

Claim 3: the sample brief turns into a page. Proof: the sample run. All three start OPEN.

The gate: robots observe, humans decide

Step 7 opens a pull request and fills docs/gate.md. The template draws a hard line between automated checks and approval.

docs/gate.md 
## What the automated checks observed

| Check | Observed | Is it an approval? |
| --- | --- | --- |
| `TEMPLATE — CI job` | `TEMPLATE — what it actually ran` | No |
| `TEMPLATE — review bot` | `TEMPLATE` | No |

## What the human read

- Success check proven by this diff: `TEMPLATE — quote the line from intent.md`
- Boundary touched by this diff: `TEMPLATE — quote the line, or NONE`
- Line from the diff that decided it: `TEMPLATE — quoted`
PLAIN ENGLISH

First, list what the machines did.

 

For each automated check: what it is, what it actually ran, and whether that counts as approval.

(Table divider.)

The CI job: pre-filled answer, No. Green CI is an observation.

An AI review bot: also No. It is printed in the template so nobody can forget.

 

Then, what a person actually read.

 

Which success check from intent.md this change proves, quoted word for word.

Whether it touches the fence. If not, write NONE explicitly.

The exact line of the diff that made up the reviewer's mind.

⚠️
Old output is not fresh evidence

The gate template ends with: "Do not treat this record, an agent claim or historical output as fresh evidence." Yesterday's green test run says nothing about today's code. Rerun it.

The SOLO loop

Walking all seven steps on your own, catching up when stuck, and why the route ends where it began.

A trail with numbered markers

A good hiking trail has numbered markers, and at each one a map showing exactly where you should be. Lost? Walk to the next marker and carry on from there.

SOLO.md is that trail for one person with their own GitHub, Linear and Notion. The markers are Git tags: step-1-intent through step-7-gate-deploy, each pointing at the reference solution after that step.

1
Plan: intent (15 min)

Claude Code interviews you one question at a time. You cut.

2
Plan: spec and contract, test first (25 min)

Quote the PDFs, write the failing test, then the code.

3
Design: one decision, a plan with proof (15 min)

Claude Code in plan mode: read-only until you accept.

4
Build: render the sample (25 min)

The first artifact: out/latest.html, no API key needed.

5
Build: the loop and one read-only tool (20 min + live run)

Take the reference files on purpose, then add one tool yourself.

6
Test: record the evidence (15 min)

Three commands, exit codes, one screenshot, one reviewer.

7
Deploy: the gate and the schedule (15 min)

Decide the gate, then run the brief every weekday morning.

The three commands you will use all day

Peek at the map. List which files the reference solution changed between empty main and the end of step 2, with a count of lines per file. (git diff.)

Compare your work. Show, line by line, how your spec differs from the reference spec.

Catch up. Copy just one file from the step 5 reference into your branch, leaving everything else as you wrote it. (git checkout.)

🧭
Catching up is part of the design

Step 5 opens with "this is the deliberate catch-up": you are told to take the reference sources.ts and agent.ts, then read them. Reading good code and adding one piece yourself teaches more than fighting an SDK for two hours.

The live run: read the log, not just the page

Step 5 ends with the first real run, using your read-only tokens from .env.

SOLO.md 
set -a && . ./.env && set +a
npm run brief 2> run.log

Read `run.log`: the `mcp=[…]` line names the connected sources, every `→`
line is a tool call. Then read `out/latest.html`.
PLAIN ENGLISH

Load every setting in .env (your tokens) as environment variables for this terminal session.

Run the real brief, and send its diagnostic output (2>, the error stream) into a file called run.log.

 

In the log, one line lists which sources connected over MCP, and each arrow line is one tool call.

Only after reading the log, read the brief itself.

The check that follows is the sharpest in the lab: "is every sentence in the brief traceable to a tool call in run.log?" A sentence with no matching tool call came from nowhere.
