How the Weather Agent Works
01

Ask About the Weather

What this little agent does, and the journey a single question takes before it comes back as an answer.

What is this thing?

You type "Wat is het weer in Amsterdam op 2026-09-21? Geef kledingadvies." and get back a friendly Dutch answer: rain is likely, bring an umbrella, wear a light jacket. That is the whole product.

Under the hood it is a starter kit for building an agent with the Claude Agent SDK. It is deliberately tiny so you can see every moving part.

🌦️

One tool

get_weather looks up temperature and chance of rain for a city and date.

☂️

One decision rule

Rain chance of 60% or more means "bring umbrella". Everything else: leave it.

🧥

One mini-quest

Add clothing advice (jas / geen jas / paraplu) by editing instructions only, no new code.

Two ways to run it

The kit has a free practice lane and a real lane. Think of a pilot: the flight simulator needs no fuel, the real plane needs a ticket (your API key).

1
Simulator lane (always runs)

Uses a built-in fixture: Amsterdam, 14°C, 72% rain. No internet, no AI, no cost.

2
Live lane (only with a key)

If ANTHROPIC_API_KEY is set in your terminal session, Claude gets the question and calls the tool.

Meet the Cast

Six files, six jobs. Knowing who does what lets you tell your AI exactly where a change belongs.

A TV weather studio

Picture the evening weather broadcast. A presenter reads from a script, a producer runs the show, a weather station supplies numbers, and a style guide says when to show the umbrella icon. This repo has exactly that crew.

src/ All the program code
agent.ts The producer: starts the run, wires Claude to the tool
decide.ts The style guide: umbrella rule and clothing rule
quest-clothing.ts The rehearsal: checks the clothing quest is done
tools/ Things Claude may ask to run
get_weather.ts The weather station: fixture data or a real HTTP lookup
tests/ Automatic checks that run with no API key

How the producer hands Claude its tools

Tools don't reach Claude one by one. agent.ts packs them into a small MCP server, like a toolbox with a label on the lid.

src/agent.ts 
export function weatherMcpServer() {
  return createSdkMcpServer({
    name: 'weather-agent-sdk',
    version: '0.1.0',
    tools: [getWeatherTool],
  });
}
PLAIN ENGLISH

Define a reusable function other files can use, called weatherMcpServer.

It builds a toolbox using a helper from the SDK...

...labels the toolbox with a name...

...and a version number...

...and puts exactly one tool inside: get_weather.

Close the toolbox.

Done.

🧭
Why this matters when steering AI

Adding a second tool means two edits: write it in src/tools/, then add it to this tools: [...] list (and to the allowed list you'll meet in Module 3). Forget either and Claude will never use it.

03

The Tool Call Handshake

How a tool describes itself to Claude, and how agent.ts runs the conversation loop.

A form at the town hall

At the town hall you can't just shout "I want a parking permit". You fill in a form with labelled boxes, and the clerk rejects it if a box is empty. A tool definition is that form: a name, a one-line purpose, and boxes Claude must fill in.

get_weather The form's name. Claude uses it to say which tool it wants.
description One sentence Claude reads to decide when this tool is useful.
city, date The boxes. Each has a type (text) and a hint for Claude.
handler The clerk who processes the form and hands back an answer.

The form, in real code

src/tools/get_weather.ts 
export const getWeatherTool = tool(
  'get_weather',
  'Fetch weather for a city and date (fixture by default for labs).',
  {
    city: z.string().describe('City name'),
    date: z.string().describe('ISO date YYYY-MM-DD'),
  },
  async (args) => {
    const weather = await fetchWeather({
      city: args.city,
      date: args.date,
      baseUrl: process.env.WEATHER_BASE_URL,
      useFixture: process.env.WEATHER_USE_FIXTURE !== '0',
    });
    return {
      content: [{ type: 'text' as const, text: JSON.stringify(weather) }],
    };
  },
);
PLAIN ENGLISH

Create a tool using the SDK's tool() helper, and share it with other files.

Its name is get_weather.

Its description, which Claude reads to decide when to use it.

Now the boxes on the form, checked by Zod:

city must be text, hinted as "City name".

date must be text, hinted as an ISO date.

End of boxes.

The clerk: an async function that receives Claude's filled-in form (args).

Wait for the real weather lookup (Module 4 opens this box)...

...passing the city Claude asked for...

...and the date...

...plus an optional real weather service address from the environment...

...and use fake data unless someone set WEATHER_USE_FIXTURE to "0".

Lookup done.

Hand the answer back...

...as a single text message containing the weather as JSON. Claude reads text, so we turn the data into text.

End of answer.

End of the clerk.

End of the tool.

Starting the conversation loop

The live lane calls the SDK's query(). It is a stream: every message in the round trip (tool request, tool result, final answer) arrives one by one, and agent.ts collects them all.

src/agent.ts 
  for await (const message of query({
    prompt,
    options: {
      systemPrompt: instructions,
      mcpServers: { weather: server },
      allowedTools: ['mcp__weather__get_weather'],
      permissionMode: 'bypassPermissions',
    },
  })) {
    messages.push(message);
  }
PLAIN ENGLISH

Start a conversation with Claude and handle each message as it arrives...

...sending your question...

...with these settings:

The system prompt is the text of instructions.md.

Plug in our toolbox and call it "weather".

Only this one tool may be used. Its full name is mcp + toolbox name + tool name.

Don't stop to ask a human "may I run this tool?" each time.

End of settings.

For every message that streams back...

...add it to our list, so we can print the last few later.

Loop finished: the conversation is over.

⚠️
The name has to match three places

mcp__weather__get_weather is built from the key weather in mcpServers and the tool name 'get_weather'. Rename either one and the allow-list silently stops matching, so Claude can't call the tool.

Fixtures and the Outside World

When the agent uses fake weather, when it goes to the real internet, and how secrets stay out of git.

Plastic fruit in the shop window

Shops put plastic fruit in the window: it looks right, never rots, and is identical every morning. The fixture is this repo's plastic fruit: Amsterdam, 14°C, 72% rain, forever.

src/tools/get_weather.ts 
/** Deterministic Amsterdam fixture — unit tests pass without network or API key. */
export const FIXTURE_WEATHER: WeatherObservation = {
  city: 'Amsterdam',
  date: '2026-09-21',
  temperatureC: 14,
  precipitationProbability: 72,
};
PLAIN ENGLISH

A note: this data is deterministic, so tests never need the internet or a key.

A shared constant shaped like a WeatherObservation:

City: Amsterdam.

Date: 21 September 2026.

14 degrees Celsius.

72% chance of rain (high enough for an umbrella).

Done.

Three doors inside fetchWeather

Every lookup walks through fetchWeather and exits through one of three doors. Which one depends on two environment variables.

1
Fixture door (default)

No WEATHER_BASE_URL set, or WEATHER_USE_FIXTURE=1. Returns the plastic fruit with your city and date pasted on.

2
Safety-net door

Fixture was switched off (WEATHER_USE_FIXTURE=0) but there's still no URL. Rather than crash, it hands back the fixture anyway.

3
Real-world door

A WEATHER_BASE_URL exists and the fixture isn't forced: it makes a real HTTP request.

src/tools/get_weather.ts 
  const response = await fetch(weatherUrl(input.baseUrl, input));
  if (!response.ok) throw new Error(`Weather request failed with ${response.status}`);
  return (await response.json()) as WeatherObservation;
PLAIN ENGLISH

Build the full address and ask the weather server, then wait for the reply.

If the server said anything other than "OK", stop loudly and include the status code (like 404 or 500) in the error.

Otherwise read the reply as JSON and trust that it has the WeatherObservation shape.

🔍
Notice the "trust"

as WeatherObservation is a promise to the compiler, not a check. If a real server returns different field names, nothing complains until something downstream reads undefined. A runtime validation step would catch it.

The live-lane function, which takes your question as text.

First, check: is there an API key in the environment?

If not, stop and ask for a key in the terminal before running the live path.

05

Rules, Quests and Tests

The plain-code rules that back up Claude, the "edit instructions, not code" quest, and the tests that keep everyone honest.

A thermostat with two dials

A thermostat doesn't think. Below the set point it heats; above it, it doesn't. decide.ts is two of those dials: one for temperature (coat or not), one for rain (umbrella or not).

src/decide.ts 
export const clothingAdvice = (weather: WeatherObservation): string => {
  const parts: string[] = [];
  if (weather.temperatureC < 12) parts.push('jas aan');
  else if (weather.temperatureC < 18) parts.push('lichte jas of trui');
  else parts.push('geen jas nodig');
  parts.push(decideWeather(weather) === 'bring umbrella' ? 'paraplu mee' : 'geen paraplu');
  return parts.join('; ');
};
PLAIN ENGLISH

A function that takes one weather reading and returns a sentence of advice.

Start with an empty list of advice pieces (an array).

Colder than 12°C? Add "jas aan" (wear a coat).

Otherwise, colder than 18°C? Add "lichte jas of trui" (light jacket or sweater).

Otherwise add "geen jas nodig" (no coat needed).

Reuse the umbrella rule (60%+ rain): add "paraplu mee" or "geen paraplu".

Glue the pieces together with a semicolon: "lichte jas of trui; paraplu mee".

Done.

💡
Same rule, two places

The 60% rule is written in code (decideWeather) and in English (instructions.md). Code gives a guaranteed answer; the prompt only asks Claude nicely. Keep both in sync, or the fixture lane and the live lane will disagree.

The quest: change the briefing, not the car

To make a sat-nav speak Dutch you change a setting, you don't rebuild the engine. The clothing quest works the same way: the README says do not add a new tool. You edit instructions.md, and a checker script confirms you did.

src/quest-clothing.ts 
if (!/kleding|clothing|jas|paraplu/i.test(instructions)) {
  console.error('Mini-quest incomplete: add clothing advice to instructions.md');
  process.exit(1);
}
PLAIN ENGLISH

Search the instructions text for any of these words: kleding, clothing, jas, paraplu (upper or lower case). This search pattern is a regex. If none are found...

...print a clear message saying what is missing...

...and quit with exit code 1, meaning "failed".

(Otherwise carry on and print the fixture advice.)

Tests: the smoke-alarm button

You press the test button on a smoke alarm without setting the house on fire. Unit tests do the same: known weather in, expected advice out, no API key, no network.

tests/weather-tool.test.ts 
test('fixture weather tool works without API key or network', async () => {
  const weather = await fetchWeather({ city: 'Amsterdam', date: '2026-09-21', useFixture: true });
  assert.equal(weather.precipitationProbability, FIXTURE_WEATHER.precipitationProbability);
  assert.equal(decideWeather(weather), 'bring umbrella');
});
PLAIN ENGLISH

A test with a name that says what it proves.

Ask the tool for Amsterdam weather, fixture mode on.

Assert the rain chance is exactly the fixture's 72.

Assert 72% rain leads to "bring umbrella".

End of test.
